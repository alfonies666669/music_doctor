# Music Doctor 0.9.9

Music Doctor редактирует теги локальных MP3 и M4A (AAC/ALAC) на macOS через TagLib 2.3.2. Music можно подключить для отбора треков, подсказок и обновления отображения после записи.

Готовая сборка предназначена для Apple Silicon с macOS 13 или новее. Для запуска достаточно системных инструментов macOS. Исходники, тесты и сборочные скрипты находятся в Git-репозитории. Готовую сборку распаковывай в отдельную папку.

## Быстрый старт

Открой Terminal в каталоге сборки. Проверь версию и доступные источники, затем создай снимок папки:

~~~sh
./music-tags --version
./music-tags doctor
./music-tags snapshot --folder '/path/to/audio' --has 'artwork=false OR composer=false' runs/selected.json
~~~

В выводе `doctor` поле `file_module` показывает состояние файлового модуля, а `music_status` — доступ к приложению. Перед первым снимком из Music разреши Terminal управлять приложением, если macOS запросит доступ.

Допиши нужные значения в том же JSON. Образец снимка и правила заполнения находятся в [examples](examples/README.md).

~~~sh
./music-tags validate runs/selected.json
./music-tags prepare runs/selected.json runs/plan.json
./music-tags preview runs/plan.json
./music-tags apply runs/plan.json
./music-tags status runs/plan.json
~~~

Для снимка из плейлиста:

~~~sh
./music-tags snapshot --music --playlist French --has 'lyrics=false' runs/french.json
~~~

Условия отбора, просмотр в консоли и диагностика описаны в [NAVIGATION.md](NAVIGATION.md). Правила редактирования запроса собраны в [examples/README.md](examples/README.md).

## Команды

| Команда | Результат |
|---|---|
| `doctor` | Версия нативного модуля и доступ к Music |
| `snapshot [фильтры] [request.json]` | Список в консоли или редактируемый запрос. При экспорте рядом создаётся `request.json.log` |
| `validate request.json` | Проверка структуры запроса и локальных вложений |
| `audit request.json [report.json]` | Список полей без целей записи |
| `prepare request.json plan.json` | Сверка SHA-256 и возможности записи, расчёт целей и фиксация вложений в `plan.json.assets/` |
| `preview plan.json` | Изменения из сохранённого плана |
| `apply plan.json` | Запись файлов, при наличии связей обновление Music, затем журнал `plan.json.journal.json` |
| `status plan.json` | Состояние журнала и сведения о незавершённых файлах |
| `inspect request-or-plan.json` | Текущие теги аудиофайлов |

Теги записывает `apply`. Команда `prepare` работает с файлами и обращается к сети только при наличии `lyrics_url`. Для каждого экспорта и нового плана укажи новый путь.

## Запрос v2

| Поле | Назначение |
|---|---|
| `version` | 2 |
| `tracks[].path`, `sha256` | Абсолютный путь и SHA-256 файла на момент снимка |
| `tracks[].tags` | Цели записи, изначально заполненные по аудиофайлу |
| `tracks[].music_suggestions` | Подсказки Music для пустых тегов. Чтобы принять значение, перенеси его в `tags` |
| `defaults`, `tracks[].fill` | Общие цели и заполнение пропусков. Приоритет `tags` → `defaults` → `fill` |
| `tracks[].artwork`, `lyrics` | Путь к JPEG/PNG или UTF-8 TXT либо состояние наличия |
| `tracks[].lyrics_url` | HTTPS-ссылка на `text/plain`. Используется при `prepare` вместо TXT |
| `tracks[].music_ids` | Связи для обновления Music после записи |

Текстовые теги `name`, `artist`, `album`, `albumArtist`, `composer`, `genre` принимают строку или список строк. Числовые теги `year`, `trackNumber`, `trackCount`, `discNumber`, `discCount` принимают целые числа от 1 до 9999. `compilation` принимает `true` или `false`. Для пропущенного тега или `null` применяется `defaults`, если он задан. `fill` применяется к отсутствующему тегу при отсутствии индивидуальной и общей цели.

Путь в `artwork` или `lyrics` задаёт вложение для записи. Путь может быть абсолютным или относительным к JSON. При неоднозначности существующей обложки или текста запись останавливается. Значения `true`, `false` и `null` отражают наличие, отсутствие или неизвестность. Поля `has`, `artwork_file`, `lyrics_file` и `from_music` принимаются в прежних запросах v2.

`prepare --force true` включает в план все заданные цели, включая совпадающие значения. SHA-256 исходника и вложения проверяются и в этом режиме.

Для v1 доступны `validate` для запросов, `audit` для снимков, `preview` и `status` для планов. Для записи собери новый снимок v2.

## Ошибки и копии

Перед атомарной заменой проверяются теги временной копии, незатронутые данные и сжатые аудиопакеты. После подтверждения файла и сохранения журнала рабочие аудиокопии удаляются. При сбое смотри `status`, `file_status` и путь `backup` в журнале. Ранее успешно записанные треки в той же группе сохраняют свои изменения.

Статус `music_status` относится к обновлению каталога. Если Music недоступен или запись в его каталоге указывает на другой файл, журнал отдельно показывает результат записи аудио и причину сбоя обновления. Синхронизация между устройствами зависит от Music.

Запись поддерживает ID3v2.2/v2.3/v2.4 без добавочных ID3v1/APE и незашифрованные однотрековые M4A. Файлы с жёсткими ссылками и неподдерживаемые наборы тегов отклоняются. Причина отображается в диагностике.

## Старые теги ID3v2.2

Если MP3 с ID3v2.2 требует записи, `prepare` добавляет в план `id3_migration: {"from": 2, "to": 3}`. `preview` показывает `ID3v2.2 → ID3v2.3`. Преобразование выполняется в `apply` на временной копии вместе с целевыми изменениями. Аудиоданные и незатронутые поля проверяются перед атомарной заменой. Переход версии записывается в журнал как `changes.id3_version`.

При отсутствии изменений файл остаётся в прежней версии. `--force true` включает совпадающие цели и тем самым может потребовать миграцию; проверки источников и сохранности данных действуют в обоих режимах. Для ID3v2.3/v2.4 сохраняется существующая версия.

Для ID3v2.2 поддержаны обычные текстовые поля (включая кириллицу), год, номера треков и дисков, комментарии, пользовательские текстовые поля, lyrics, картинки, идентификатор записи, счётчик и рейтинг, основные URL. Неизвестные/устаревшие поля и заголовки со сжатием или unsynchronisation отклоняются при `prepare` с путём файла. Миграция таких файлов требует отдельной обработки: молча удалять поля нельзя. Проверка raw-инвентаря и содержимого кадров остаётся обязательной.

`validate` проверяет структуру запроса и вложения; возможность записи исходника проверяет `prepare`. Старые планы для ID3v2.2 без явной миграции нужно пересоздать. После внешней конвертации теги и SHA-256 файла меняются: нужен актуальный снимок с повторным переносом выбранных целей; обходить проверку хеша нельзя.

## Сборка

На Mac с инструментами разработчика Apple и CMake 3.24+:

~~~sh
cmake -S native -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_OSX_ARCHITECTURES=arm64
cmake --build build --parallel
./music-tags doctor
./native/package.sh
~~~

CMake проверяет SHA-256 архива TagLib 2.3.2 с utf8cpp 4.2.0. В сборке используется системная zlib. `native/package.sh` кладёт дистрибутив в `dist/`.

Для разработки:

~~~sh
node --test --test-concurrency=1 tests/core.test.js tests/adapter.test.js tests/filters.test.js tests/snapshot.test.js tests/file-workflow.test.js tests/id3-migration.test.js
osascript -l JavaScript tests/native.test.js "$PWD"
~~~

Сквозные тесты запускаются последовательно, поскольку `apply` использует общую блокировку от одновременной записи. Для сквозных тестов нужны Node.js, собранный файловый модуль и FFmpeg для генерации синтетических файлов. Тесты Music используют заглушки. Для проверки живого обновления используй отдельный трек в Music.
